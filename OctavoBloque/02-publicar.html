    Antes de empezar

    Qué es desplegar, de verdad

    Cuatro ideas que convierten «subir la web» en un oficio.

    Correspondencias ↗El plano · deploy↗Entornos↗Versión ilustrada

    El recorrido de un cambio

    1 · CommitGuardas en GitHub

    Cada cambio queda registrado con un mensaje.

    2 · BuildVercel prepara

    Copia tus archivos y monta la versión nueva (con HTML y CSS, casi instantáneo).

    3 · DeploySe publica

    La versión queda en la red de servidores de Vercel (CDN) con su propia dirección.

    4 · ProducciónSe asigna el dominio

    Tu dirección principal pasa a apuntar a esa versión.

    Las cuatro ideas clave

    1. Cada despliegue es una foto fija. Vercel no «sobrescribe» tu web: crea una versión nueva y completa, con su propia dirección única, y las anteriores siguen existiendo.
    2. Producción es un cartel que se mueve. Tu dirección principal (libro-de-visitas.vercel.app) es un alias que apunta a la última versión buena. Publicar es mover el cartel; volver atrás, también.
    3. Todo sale del repositorio. Lo que no está en GitHub no existe para Vercel. Por eso nunca se editan archivos «en el servidor».
    4. Cada rama, un entorno. La rama main es producción; cualquier otra rama genera una vista previa con su dirección.
    🎞️

    Es como un rollo de fotos de carné: cada despliegue es una foto nueva y nunca se tiran las anteriores. El escaparate (producción) enseña la que tú eliges. Si la nueva sale mal, vuelves a colgar la de antes en un segundo.

    1

    Misión 1

    El repositorio en GitHub

    Tu carpeta libro-de-visitas, en la nube y con historial.

    Correspondencias ↗La carpeta↗Pantallas de GitHub
    Misión 110 minutos
    1. En GitHub, botón + → New repository. Nombre: libro-de-visitas. Visibilidad Public. Pulsa Create repository.
    2. Pulsa el enlace uploading an existing file. Abre tu carpeta en el explorador, selecciona todo lo de dentro (no la carpeta) y arrástralo.
    3. Escribe un mensaje de commit que diga qué subes («Primera versión del libro de visitas») y pulsa Commit changes.
    4. Comprueba que index.html, .gitignore y README.md están en la raíz, junto a las carpetas css y js.

    Comprueba: en la portada del repositorio se ve tu README.md y la lista de archivos empieza por las carpetas y sigue con index.html. No hay ningún archivo .env.

    Si algo falla
    Todo quedó dentro de una carpeta libro-de-visitas/
    Arrastraste la carpeta, no su contenido. Bórrala del repositorio o crea uno nuevo y repite arrastrando lo de dentro.
    No se ven .gitignore ni .env.example
    El explorador de Windows esconde los archivos que empiezan por punto. Actívalos en Vista → Mostrar → Elementos ocultos antes de arrastrar, o súbelos uno a uno con Add file → Upload files.
    2

    Misión 2

    Importar en Vercel

    Conectar el repositorio y obtener tu primera dirección pública.

    Correspondencias ↗Pantallas de Vercel↗CDN
    Misión 210 minutos
    1. En vercel.com: Add New… → Project.
    2. En la lista de repositorios, Import en libro-de-visitas. Si no aparece, pulsa Adjust GitHub App Permissions y dale acceso.
    3. Revisa la configuración: Framework Preset Other (es HTML y CSS, no hay nada que construir) y Root Directory ./.
    4. Pulsa Deploy y espera el confeti.
    5. Abre la dirección ….vercel.app y apúntala en tu gestor: la usarás en Supabase (página 07).

    Comprueba: tu web se abre en el móvil desde la dirección .vercel.app, con candado (HTTPS) y con su CSS.

    Si algo falla
    404: NOT_FOUND
    No hay index.html en la raíz del repositorio (misión 1) o se llama distinto (Index.html).
    La web sale sin estilos
    La ruta del CSS no coincide letra a letra (mayúsculas). En el servidor, Estilos.css y estilos.css son archivos distintos.
    No puedo importar el repositorio
    El plan Hobby solo conecta repositorios de tu cuenta personal, no de una organización de GitHub.

    Misión 3

    El despliegue automático

    Desde ahora, cada commit en main se publica solo. Míralo pasar.

    Vercel quedó «escuchando» tu repositorio. Cada vez que llega un commit a main, hace el recorrido completo: build, despliegue y asignación del dominio. Tú no vuelves a subir nada a Vercel nunca más.

    EstadoQué significa
    QueuedEn cola: espera su turno (en Hobby, un despliegue a la vez).
    BuildingPreparando la versión.
    ReadyPublicada. Si es de main, ya está en producción.
    ErrorAlgo falló: no se publica nada y producción sigue con la versión anterior.
    CanceledCancelado (por ejemplo, porque llegó otro commit más nuevo).

    Fíjate en el detalle de seguridad: si un despliegue falla, tu web no se rompe, porque el dominio sigue apuntando a la última versión buena.

    Misión 310 minutos
    1. Abre en Vercel tu proyecto, pestaña Deployments, y déjala abierta.
    2. En GitHub, abre index.html, pulsa el lápiz (Edit), cambia el texto del <h1> y pulsa Commit changes.
    3. Vuelve a Vercel: aparece un despliegue nuevo que pasa por Building hasta Ready.
    4. Recarga tu web (si no ves el cambio, Ctrl+F5: es la caché).

    Comprueba: en Deployments hay dos despliegues, el primero y el de tu cambio, y la web publicada enseña el título nuevo.

    Misión 4

    Leer un despliegue

    Cada despliegue cuenta su historia: qué commit, qué archivos, qué pasó.

    Correspondencias ↗Códigos de estado↗DevTools
    • Dirección única: cada despliegue tiene la suya (algo como libro-de-visitas-a1b2c3-tu-usuario.vercel.app), que siempre enseña esa versión. Sirve para comparar el antes y el después.
    • Source: el commit y el mensaje que lo provocó. Por eso importa escribir buenos mensajes.
    • Build Logs: el registro paso a paso. Si algo falla, el motivo está aquí, normalmente en las últimas líneas en rojo.
    • Source / Output: la lista de archivos que se publicaron. Si un archivo falta aquí, no existe en tu web.
    Misión 45 minutos
    1. En Deployments, pulsa el despliegue más reciente.
    2. Abre su dirección única (botón Visit o la URL larga) y compárala con la de producción.
    3. Abre Build Logs y lee las líneas: verás que copia tus archivos y termina sin errores.
    4. Busca en la lista de archivos publicados tu css/estilos.css.

    Misión 5

    Vistas previas por rama

    Probar un cambio en una dirección aparte, sin tocar la web de verdad.

    Correspondencias ↗Local, preview, producción

    Una rama es una copia paralela del código donde puedes cambiar cosas sin afectar a main. El bloque 09 (Git) las explica a fondo, pero GitHub deja crearlas desde la web, y Vercel genera una vista previa para cada una.

    Protección

    Por defecto, Vercel protege las vistas previas: para abrirlas hay que haber iniciado sesión en Vercel con permiso sobre el proyecto. Si un compañero no puede verla, es eso. Se cambia en Settings → Deployment Protection; para clase, mejor dejarlo así.

    Misión 510 minutos
    1. En GitHub, edita css/estilos.css (lápiz) y cambia un color.
    2. Al guardar, elige Create a new branch for this commit and start a pull request, con un nombre como prueba-color, y pulsa Propose changes y luego Create pull request.
    3. En unos segundos, Vercel deja un comentario en el pull request con el enlace a la Preview. Ábrelo: ves el color nuevo.
    4. Abre tu dirección de producción: sigue con el color de antes.
    5. Si te gusta, pulsa Merge pull request: el cambio entra en main y Vercel lo publica en producción. Si no, Close pull request.

    Comprueba: durante unos minutos conviven dos versiones de tu web: la de producción y la vista previa. Así se trabaja en los equipos profesionales.

    Misión 6

    Volver a la versión anterior

    Has publicado algo roto. En un clic, la web vuelve a como estaba.

    Como cada despliegue es una foto fija, deshacer es tan sencillo como volver a apuntar el dominio a la foto anterior. Vercel lo llama Instant Rollback.

    • En el plan Hobby solo se puede volver a la versión inmediatamente anterior de producción.
    • Después de volver atrás, Vercel deja de publicar solos los commits nuevos de main, para no pisar tu arreglo de emergencia. Cuando hayas corregido el error, hay que deshacer la vuelta atrás para recuperar la publicación automática.
    ⏪

    Es el botón de «deshacer» de la web entera. Pero, como en un procesador de textos, después de deshacer conviene arreglar el original: la vuelta atrás es un parche, no la solución.

    Misión 610 minutos
    1. Rompe algo a propósito: en GitHub, cambia en index.html el enlace al CSS por css/no-existe.css y haz commit. Espera a que se publique: tu web sale sin estilos.
    2. En la portada del proyecto en Vercel, en el recuadro de producción, pulsa Instant Rollback, elige la versión anterior y confirma.
    3. Recarga tu web: vuelve a tener estilos al instante.
    4. Arregla el enlace en GitHub y haz commit (verás que no se publica solo).
    5. En el recuadro de producción pulsa Manage, elige el despliegue nuevo y confirma: vuelve la publicación automática.

    Comprueba: sabes volver atrás en segundos y sabes reactivar la publicación automática. Es lo primero que se hace cuando algo se rompe en producción.
