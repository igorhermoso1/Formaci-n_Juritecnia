    Misión 1

    Revisar el estado de seguridad

    Antes de abrir puertas, comprueba que todas están cerradas.

    Correspondencias ↗Qué es RLS (y simulador)↗Claves

    Recordatorio en tres líneas

    • Desde la web se llega con la clave publicable: rol anon (sin sesión) o authenticated (con sesión).
    • Con RLS activado y sin reglas, la respuesta a todo es «no».
    • Cada regla (policy) abre una acción concreta (select, insert, update, delete) para un rol concreto, con una condición.

    Si no lo tienes claro, juega primero con el simulador del portero del plano.

    Misión 15 minutos
    1. Abre Table Editor: mensajes y temas deben mostrar que el RLS está activado.
    2. Abre Advisors → Security Advisor y pulsa para actualizar el análisis. Si avisa de «RLS disabled» en alguna tabla, actívalo en esa tabla (Edit table).
    3. Lee los avisos «RLS enabled, no policy»: es justo lo que vas a arreglar ahora.

    Misión 2

    Reglas con el panel

    Las dos reglas del libro de visitas: todos leen, todos escriben; nadie edita ni borra.

    Las reglas que necesita el proyecto

    TablaAcciónParaCondición¿Por qué?
    mensajesSELECTanon, authenticatedtrue (todas las filas)Los mensajes se muestran en la web
    mensajesINSERTanontrue (la tabla ya limita la longitud)Cualquiera puede firmar
    temasSELECTanon, authenticatedtruePara elegir tema en el formulario
    (ninguna)UPDATE · DELETE——Solo tú, desde el panel
    Misión 210 minutos
    1. Abre Authentication → Policies (en algunas versiones, Database → Policies; o, desde la tabla, el botón Add RLS policy).
    2. En mensajes, pulsa Create policy (o New policy). Elige la plantilla «Enable read access for all users»: acción SELECT, roles anon y authenticated, expresión true. Revisa y guarda.
    3. Otra regla en mensajes: nombre «Cualquiera puede dejar un mensaje», acción INSERT, rol anon, expresión WITH CHECK true. Guarda.
    4. En temas, crea una regla de lectura igual que la primera.

    Comprueba: en la lista de Policies, mensajes tiene 2 reglas y temas 1. En Security Advisor desaparece el aviso «no policy».

    Si algo falla
    ¿USING o WITH CHECK?
    USING decide qué filas existentes se pueden ver, cambiar o borrar. WITH CHECK decide si una fila nueva o modificada es aceptable. Para INSERT solo hay WITH CHECK; para SELECT y DELETE, solo USING.
    No encuentro las plantillas
    Escribe la regla en blanco: los campos son los mismos (nombre, acción, roles y expresión). O usa el SQL de la misión 3.

    Misión 3

    Las mismas reglas con SQL

    Un script repetible: para el proyecto de producción y para tu repositorio.

    Correspondencias ↗Script de tablas↗Data API
    ¿Por qué grant?

    Las reglas RLS filtran, pero antes el rol necesita permiso sobre la tabla. Si en tu proyecto está activado «Automatically expose new tables» (página 04), ese permiso ya existe y el grant no cambia nada; si está desactivado, sin grant verás el error 42501 permission denied for table. Ponerlo siempre hace el script válido en los dos casos.

    Misión 35 minutos
    1. En SQL Editor → New query, pega el script y llámalo «Seguridad libro de visitas».
    2. Run. Como empieza borrando las reglas si existen, no choca con las que creaste en la misión 2.
    3. Guarda una copia en tu carpeta: supabase/seguridad.sql, junto a estructura.sql.

    Misión 4

    Probar las reglas como un visitante

    El SQL Editor puede «ponerse el disfraz» de otro rol. Así compruebas tus reglas sin escribir la web.

    Normalmente el SQL Editor trabaja como postgres (administrador, sin reglas). Junto al botón Run hay un selector de rol: elige anon y las consultas se ejecutarán como si vinieran de tu web sin sesión.

    Misión 410 minutos
    1. Pega las consultas en una consulta nueva y cambia el selector de rol a anon.
    2. Ejecuta la 1 (selecciónala y Run selected, o ejecútalas de una en una): ves los mensajes.
    3. Ejecuta la 2: se inserta. Compruébalo en el Table Editor.
    4. Ejecuta la 3 y la 4: el resultado dice 0 filas afectadas. RLS no da error al borrar o cambiar: simplemente no encuentra filas permitidas.
    5. Vuelve el selector a postgres y borra a mano la fila «Prueba anon».

    Comprueba: como anon puedes leer y añadir, pero borrar y cambiar afectan a 0 filas. Tus mensajes siguen intactos.

    Si algo falla
    «new row violates row-level security policy for table "mensajes"»
    No hay regla de INSERT para ese rol, o su with check no se cumple. Revisa la misión 2 o 3.
    «permission denied for table mensajes» (código 42501)
    Falta el grant. Ejecuta la parte de permisos del script de la misión 3.
    No veo el selector de rol
    Puede estar en el menú del botón Run o arriba a la derecha del editor. Si tu versión no lo tiene, probarás las reglas desde la web en la página 08.

    Misión 5

    Usuarios y direcciones permitidas

    Prepara el inicio de sesión para que funcione en tu ordenador y en tu web publicada.

    Correspondencias ↗Auth en el plano↗Login en la web

    Cómo entra un usuario

    Con el enlace mágico, la persona escribe su correo, recibe un enlace y, al pulsarlo, vuelve a tu web con la sesión iniciada. Para que ese «volver» funcione, Supabase necesita saber a qué direcciones puede devolverla: si no está en la lista, la manda a la Site URL o rechaza la redirección. Es una medida de seguridad: evita que alguien use tu proyecto para mandar gente a una web trampa.

    AjusteValor para tu proyectoPor qué
    Site URLhttps://libro-de-visitas.vercel.app (tu dirección de Vercel)La dirección por defecto de los correos de confirmación y recuperación.
    Redirect URLshttp://127.0.0.1:5500/**Live Server en tu ordenador.
    Redirect URLshttp://localhost:5500/**Por si Live Server abre con «localhost».
    Redirect URLshttps://libro-de-visitas.vercel.app/**Tu web publicada.
    Redirect URLshttps://*-tu-usuario.vercel.app/**Las vistas previas de Vercel (cambia «tu-usuario» por tu cuenta).

    ** admite cualquier ruta detrás (/carta.html, /a/b); * solo un trozo. En producción, cuanto más exacta la dirección, mejor.

    Correos

    El servicio de correo que trae Supabase de serie está muy limitado y es solo para pruebas: envía pocos correos por hora. Para una web real se configura un servicio propio en Authentication → Emails → SMTP Settings (Resend, Brevo…).

    Misión 510 minutos
    1. Authentication → Sign In / Providers: comprueba que Email está activado. Para practicar, puedes desactivar Confirm email; en producción, déjalo activado.
    2. Authentication → URL Configuration: en Site URL pon tu dirección de Vercel (si aún no la tienes, deja http://127.0.0.1:5500 y cámbiala en la página 09).
    3. En Redirect URLs, pulsa Add URL y añade las direcciones de la tabla, adaptadas a tu proyecto.
    4. Authentication → Users → Add user → Send invitation (o Create new user) con tu propio correo, para tener un usuario de prueba.

    Comprueba: en Users aparece tu usuario y en URL Configuration están tu dirección local y la de Vercel.

    Misión 6 · ampliación

    Reglas por usuario

    «Solo los usuarios con sesión escriben, y cada uno borra solo lo suyo».

    La clave es auth.uid(): dentro de una regla, devuelve el identificador del usuario que hace la petición (o nada si es anónimo). Se guarda en cada fila en una columna autor y se compara.

    Misión 610 minutos · opcional
    1. Decide si tu libro de visitas será abierto (cualquiera firma) o con usuarios (hay que entrar). Para empezar, abierto es más sencillo.
    2. Si eliges «con usuarios», ejecuta este script en el proyecto de pruebas.
    3. Prueba con el rol anon a insertar: ahora debe fallar con «new row violates row-level security policy».

    Misión 7 · ampliación

    Archivos con Storage

    Un cubo de fotos donde solo suben los usuarios con sesión, y todo el mundo puede verlas.

    Correspondencias ↗Storage en el plano↗Límites

    En un cubo público, cualquiera con el enlace puede ver un archivo, pero subir, cambiar o borrar sigue necesitando reglas. Los archivos viven en la tabla especial storage.objects, y las reglas se escriben sobre ella.

    Misión 710 minutos · opcional
    1. Storage → New bucket: nombre fotos, marca Public bucket.
    2. En las opciones del cubo, limita el tamaño (File size limit: 2 MB) y los tipos (Allowed MIME types: image/webp, image/jpeg, image/png).
    3. Sube una foto a mano con Upload file y copia su enlace público (Get URL). Ábrelo en una pestaña de incógnito: se ve.
    4. Ejecuta la regla de arriba en el SQL Editor para permitir subidas a usuarios con sesión.

    Comprueba: la foto se ve con su enlace público en incógnito, y el cubo rechaza archivos de más de 2 MB o de otros tipos.
