    ¿Qué es el deploy?

    La palabra que más vas a oír cuando una web sale de tu ordenador. Y la que menos se explica.

    Correspondencias 02La petición08Supabase19Proyecto final▶Manual 02 · Publica tu web

    De «funciona en mi ordenador» a «funciona para todo el mundo»

    Deploy (en castellano, despliegue) es el proceso de llevar tu web desde tu ordenador hasta un sitio donde cualquiera pueda usarla, y de mantenerla viva allí. En la práctica, un deploy tiene dos mitades. La primera es publicar: GitHub guarda los archivos y Vercel los sirve al mundo (páginas 02 y 03 del manual). La segunda es todo lo que rodea a la web publicada:

    • Entender el viaje: qué pasa entre que alguien escribe tu dirección y ve tu página.
    • Saber qué hay detrás: frontend, backend, base de datos, y por qué casi nunca necesitas montar un servidor propio.
    • Guardar datos de verdad: con Supabase, los mensajes de un formulario dejan de perderse y se guardan en una base de datos.
    • Proteger: claves, secretos y reglas de acceso, para que nadie lea ni borre lo que no debe.
    • Mantener: que sea rápida, legal, segura y que no te cueste dinero por sorpresa.
    🚇

    Piensa en este bloque como la red de metro de una ciudad. Tu web es un pasajero. Hay líneas para moverse (la red), estaciones donde se guardan cosas (los datos), torniquetes que controlan quién pasa (la seguridad) y servicios en los andenes (correo, pagos, estadísticas). Cada estación tiene un letrero de correspondencias: así ves qué conecta con qué.

    Línea 1 · Fundamentos

    El viaje de una petición

    Escribes una dirección, pulsas Intro y en medio segundo aparece una página. Han pasado siete cosas.

    Correspondencias ▶Manual 01 · DevTools 05CDN y caché16Rendimiento↗DNS y dominio

    Cliente y servidor

    Toda la web funciona con una conversación de dos: el cliente (el navegador, que pide) y el servidor (un ordenador que responde). El idioma en el que hablan se llama HTTP; con el candado (cifrado), HTTPS. Cada pregunta del navegador es una petición (request) y cada contestación, una respuesta (response).

    🍽️

    Es un restaurante: tú (el navegador) pides a la camarera «la carta, por favor» (petición) y ella vuelve con la carta (respuesta). Luego pides el primer plato, el segundo, el pan… Una web normal hace decenas de peticiones: el HTML, luego cada CSS, cada imagen, cada fuente.

    Simulador: sigue la petición paso a paso

      Los códigos de estado: el semáforo de cada respuesta

      Cada respuesta lleva un número de tres cifras que dice qué ha pasado. La primera cifra es la familia: 2 = bien, 3 = ve a otro sitio, 4 = el error es tuyo (del cliente), 5 = el error es del servidor. Pulsa cada uno:

      Míralo tú

      En cualquier web: F12 → pestaña Red (Network) → recarga. Verás cada petición, su código y cuánto tardó. Es la herramienta número uno para entender un deploy que falla.

      Línea 1 · Fundamentos

      Frontend, backend y base de datos

      Las tres capas de cualquier aplicación web. Hasta ahora has trabajado en la primera.

      Correspondencias 04Arquitecturas08Supabase14Funciones

      El restaurante completo

      🪑Lo que vesFrontend

      La sala: mesas, carta, decoración. Es HTML, CSS y JavaScript que se ejecuta en el navegador de cada visitante. Todo lo que hay en el frontend se puede ver (pulsa Ctrl+U en cualquier web).

      👩‍🍳Lo que procesaBackend

      La cocina: recibe los pedidos, decide, comprueba, calcula. Se ejecuta en un servidor, y el visitante no puede verlo. Ahí van las cosas secretas: contraseñas, pagos, envío de correos.

      🗄️Lo que recuerdaBase de datos

      La despensa y el libro de reservas: guarda la información de forma ordenada y permanente (mensajes, usuarios, pedidos) para que siga ahí mañana.

      Una web estática (las que has hecho hasta ahora) es solo sala: el HTML ya está escrito y se sirve igual a todo el mundo. En cuanto quieres guardar algo (un mensaje, un usuario, un pedido), necesitas despensa y, a menudo, cocina.

      Juego: ¿en qué capa vive?

      Para cada cosa, elige dónde pasa o dónde se guarda.

      Y la respuesta a la gran pregunta: ¿tengo que aprender PHP?

      De la más sencilla a la más completa

      ArquitecturaCómo funcionaEjemplosCuándo
      1 · EstáticaArchivos HTML, CSS e imágenes ya hechos. El hosting solo los entrega.Tu portafolio en Vercel o GitHub PagesWebs informativas, portafolios, landings. Gratis y rapidísimo.
      2 · Estática + servicios (BaaS)La web sigue siendo estática, pero habla con un servicio que hace de despensa y de portero: base de datos, usuarios, archivos.Tu web + Supabase (o Firebase)El camino de este bloque. Formularios que guardan, zonas con usuarios, listas que se actualizan.

      BaaS = Backend as a Service, «backend como servicio»: alguien ya ha construido la cocina y tú la alquilas.

      ¿Y PHP?

      PHP es el lenguaje de servidor más extendido del mundo: según W3Techs, lo usa el 68,1 % de las webs cuyo lenguaje de servidor se conoce (dato de noviembre de 2026). La razón principal se llama WordPress, el gestor de contenidos que mueve una parte enorme de internet.

      Entonces, ¿hay que aprenderlo? Para lo que vais a construir, no:

      • PHP necesita un servidor que lo ejecute (un hosting con PHP). Vercel y GitHub Pages, donde publicáis, sirven webs estáticas, no PHP.
      • Lo que la gente hacía con PHP (guardar un formulario, tener usuarios) hoy se resuelve con Supabase desde una web estática, sin mantener servidor.
      • Si algún día trabajas con WordPress, lo que sí te servirá es todo lo que sabes de HTML y CSS: los temas de WordPress son HTML y CSS con PHP alrededor.
      En una frase

      PHP es historia viva y conviene saber que existe. Vuestro camino moderno es web estática + Supabase + funciones cuando haga falta.

      Línea 2 · Alojamiento y red

      CDN, caché y edge

      Lo que Vercel hace sin que lo veas cada vez que publicas.

      Correspondencias ▶Manual 03 · Producción 02La petición16Rendimiento18Costes

      Copias de tu web por todo el mundo

      Si tu web viviera en un único servidor en Madrid, a alguien en Japón cada petición le haría cruzar medio planeta. Una CDN (Content Delivery Network, red de distribución de contenido) guarda copias de tus archivos en cientos de ciudades. Cada visitante recibe la copia más cercana. Vercel, Netlify y GitHub Pages ya tienen la suya: por eso tu web vuela sin que configures nada.

      🏪

      Es una cadena de supermercados: en vez de que todo el país vaya a la fábrica a por leche, hay una tienda en cada barrio con el mismo producto.

      Caché: guardar para no volver a pedir

      La caché es una copia guardada «por si acaso». Hay caché en la CDN y caché en el navegador de cada visitante. Por eso, a veces, publicas un cambio y no lo ves: tu navegador te enseña la copia vieja. Solución: Ctrl + F5 (recarga forzada) o esperar.

      Edge: el borde de la red

      «Edge» es el nombre de esos servidores repartidos por el mundo, los más cercanos a cada persona. Cuando leas «edge functions», piensa: código que se ejecuta en el servidor más cercano al visitante (estación 14).

      Lo que esto significa para ti

      • Las imágenes pesadas se copian por todo el mundo y gastan el tráfico mensual de tu plan: optimízalas (WebP, tamaño justo). Estación 16 y 18.
      • Si cambias un archivo y «no se actualiza», casi siempre es caché, no un error.
      • Los datos que cambian (mensajes, usuarios) no van en la CDN: van en la base de datos (línea 3).

      El despliegue por dentro

      1 · CommitGitHub

      Guardas un cambio con su mensaje.

      2 · BuildVercel prepara

      Copia los archivos y monta la versión.

      3 · DeployVersión fija

      Una foto completa de tu web, con su propia dirección única.

      4 · AliasProducción

      Tu dominio pasa a apuntar a esa foto.

      • Cada despliegue es inmutable: no se sobrescribe nada; las versiones anteriores siguen existiendo.
      • Producción es un cartel que se mueve: publicar es mover el dominio a la versión nueva; volver atrás (Instant Rollback) es moverlo a la anterior.
      • Si un despliegue falla, la web no se rompe: el dominio sigue en la última versión buena.

      Todo esto lo montas y lo pruebas en la página 02: despliegue automático, registros, vistas previas y vuelta atrás.

      Los tres entornos

      1 · LocalTu ordenador

      localhost con Live Server. Rompes, pruebas, vuelves a romper. Nadie lo ve.

      2 · Vista previaPreview

      Una copia publicada con dirección propia para enseñar o probar un cambio antes de que llegue a todos. Vercel crea una por cada rama distinta de main.

      3 · ProducciónLa web real

      La dirección que conoce todo el mundo. Lo que hay en la rama main. Aquí no se experimenta.

      🎭

      Es un teatro: local es ensayar en casa, preview es el ensayo general con el decorado puesto y unos pocos invitados, y producción es el estreno con el público pagando entrada.

      El flujo completo de un cambio

      1. Cambias el código en tu ordenador y lo pruebas con Live Server (local).
      2. Lo subes a GitHub en una rama aparte (las ramas son del bloque 09, Git) → Vercel crea una preview con su propia dirección.
      3. Lo revisas tú o tu equipo en esa dirección.
      4. Lo juntas con main → Vercel publica en producción.

      Mientras no uséis ramas, trabajaréis directamente en main: cada commit va a producción, como en la página 02 del manual. Por eso conviene probar bien en local antes de subir.

      Cada entorno, sus propios datos

      Los profesionales nunca prueban con los datos reales. Con Supabase, lo ideal es tener un proyecto para pruebas y otro para producción (el plan gratuito permite dos proyectos activos, justo lo necesario). Así, si una prueba borra la tabla, no se pierden los mensajes de verdad.

      Línea 4 · Seguridad

      Secretos y variables de entorno

      La regla de oro del deploy: lo que está en el frontend lo puede leer cualquiera.

      Correspondencias ▶Manual 07 · Seguridad 11RLS14Funciones17Seguridad y ley

      Claves públicas y claves secretas

      Los servicios (Supabase, pagos, correo, mapas…) te dan claves: textos largos que identifican tu proyecto. Hay dos tipos y no se pueden confundir:

      Pública

      Hecha para ir en la web. Cualquiera puede verla (está en tu HTML). Solo da acceso a lo que tus reglas permitan. Ejemplo: la clave publicable de Supabase (sb_publishable_…).

      Secreta

      Da acceso total. Jamás en el HTML, ni en el repositorio, ni en una captura. Solo en el servidor. Ejemplo: la clave secreta de Supabase (sb_secret_…) o la contraseña de la base de datos.

      Muy importante

      Si una clave secreta llega a GitHub, dala por robada, aunque borres el archivo enseguida: queda en el historial y hay robots que rastrean GitHub buscando claves. Lo único que sirve es revocarla (anularla) en el servicio y crear otra.

      Variables de entorno

      Una variable de entorno es un valor que se guarda fuera del código, en la configuración de la plataforma, y que el código lee al construirse o al ejecutarse en el servidor. Sirve para dos cosas: que los secretos no estén en el repositorio y que cada entorno (estación 06) tenga sus propios valores.

      • En tu ordenador se guardan en un archivo .env (o .env.local), que nunca se sube: se añade a .gitignore (lo verás en el bloque 09, Git).
      • En Vercel: proyecto → Settings → Environment Variables. Eliges en qué entornos se usa cada una: Production, Preview, Development.
      • Un cambio en las variables no afecta a lo ya publicado: hay que volver a desplegar (Redeploy).

      La trampa de las webs estáticas

      Las variables de entorno de Vercel llegan al proceso de construcción y a las funciones del servidor. Una web estática de HTML y CSS no tiene ninguna de las dos cosas: el navegador no puede leer esas variables. Esto tiene dos consecuencias que lo ordenan todo:

      1. La clave publicable de Supabase se escribe directamente en tu código de la web. Está bien: está hecha para eso, y lo que la protege son las reglas RLS (estación 11).
      2. La clave secreta solo puede vivir en una variable de entorno de una función serverless (estación 14). Si una tarea necesita la clave secreta, necesita una función.

      Juego: ¿se puede publicar?

      Para cada dato, decide si puede ir en el HTML de tu web (público) o si es secreto.

      Diseñar dónde se guarda cada dato es la mitad del trabajo de un backend.

      Una base de datos es un archivador de hojas de cálculo

      • Una tabla es una hoja: mensajes, inscripciones, productos.
      • Cada columna es un dato con un tipo fijo: texto, número, fecha, sí/no.
      • Cada fila es un registro: un mensaje concreto, una inscripción concreta.
      • Cada fila tiene un identificador único, la clave primaria (id), como el DNI de esa fila.

      La clave para diseñar una tabla está en el formulario que la va a rellenar: cada campo del formulario es una columna. Si tu formulario tiene name="nombre" y name="mensaje", tu tabla tendrá las columnas nombre y mensaje.

      RLS: el portero de cada fila

      La estación más importante del bloque. Sin ella, tu base de datos es una puerta abierta.

      Correspondencias ▶Manual 07 · Seguridad 07Secretos12Usuarios17Seguridad y ley

      ¿Por qué la clave publicable no es peligrosa?

      Recuerda (estación 07): la clave publicable va en tu HTML y cualquiera puede copiarla. Entonces, ¿qué impide que alguien la use para borrar todos tus mensajes? Las reglas RLS (Row Level Security, seguridad a nivel de fila).

      Cada petición que llega a Supabase trae una clave, y Supabase la traduce a un papel (rol):

      Quién llamaPapel¿Se le aplican las reglas?
      Clave publicable, sin iniciar sesiónanon (anónimo)Sí
      Clave publicable, con sesión iniciadaauthenticatedSí
      Clave secretaservice_roleNo: se salta todas las reglas. Por eso es secreta.

      Con RLS activado y sin ninguna regla, la respuesta a todo es «no»: nadie puede leer ni escribir con la clave publicable. Luego abres solo las puertas que necesites, una a una. Es como un local con todas las puertas cerradas por defecto, donde el portero tiene una lista: «los anónimos pueden dejar mensajes», «todos pueden leer mensajes», «nadie puede borrar».

      Auth: la recepción del edificio

      Supabase Auth guarda los usuarios en su propia tabla protegida y se encarga de lo difícil: guardar las contraseñas cifradas, enviar el correo de confirmación, recuperar la contraseña. Formas de entrar (en Authentication → Sign In / Providers):

      • Correo y contraseña: la clásica, con correo de confirmación.
      • Enlace mágico (magic link): te llega un enlace al correo y entras sin contraseña.
      • Cuentas de terceros (OAuth): «Entrar con Google», «con GitHub»… Requiere configurar una app en ese servicio.

      Cuando alguien inicia sesión, sus peticiones pasan de anon a authenticated, y en las reglas puedes usar auth.uid(), el identificador de esa persona. Así se escribe «cada uno solo puede borrar lo suyo»:

      Los archivos (fotos, PDF, avatares) no van en las tablas: van en Storage, organizados en cubos (buckets):

      Línea 5 · Servicios

      Funciones serverless

      Un trocito de backend que solo existe mientras alguien lo llama.

      Correspondencias 07Secretos04Arquitecturas15Servicios

      ¿Cuándo necesitas una?

      La regla sale de la estación 07: si una tarea necesita una clave secreta, no puede hacerse en el navegador. Ejemplos:

      • Enviar un correo de confirmación (la clave del servicio de correo es secreta).
      • Cobrar con tarjeta (la clave secreta de la pasarela de pago).
      • Hacer algo con permisos de administrador en Supabase (la clave secreta).
      • Llamar a una API privada (de inteligencia artificial, de un ERP…) o tareas programadas («cada lunes, borra los mensajes de más de un año»).

      «Serverless» no significa que no haya servidor: significa que no tienes que mantenerlo. Escribes la función, la plataforma la ejecuta cuando llega una petición y se apaga al terminar. Solo «existe» unos milisegundos.

      🛎️

      Es un servicio de habitaciones: no tienes un cocinero en tu cuarto todo el día. Llamas, alguien prepara lo que pides con los ingredientes de la cocina (los secretos), te lo sube y se va.

      Dónde viven

      Vercel Functions: archivos dentro de una carpeta api/ de tu repositorio. Vercel los convierte en funciones y lee los secretos de sus variables de entorno. Encaja con lo que ya publicas en Vercel.

      Supabase Edge Functions: funciones dentro de tu proyecto de Supabase, cerca de tu base de datos. Se escriben en TypeScript (JavaScript con tipos). 500.000 llamadas al mes gratis.

      El flujo completo

      Navegador → /api/enviar-correo (tu función, con el secreto en una variable de entorno) → servicio de correo. El navegador nunca ve la clave: solo ve la respuesta «enviado».

      Línea 6 · Producción · y Línea 4 · Seguridad

      Seguridad y ley

      En cuanto guardas el nombre o el correo de alguien, entras en el terreno del RGPD.

      Correspondencias ▶Manual 03 · Cabeceras de seguridad 07Secretos11RLS09Región UE

      Seguridad: la lista mínima

      1. HTTPS siempre. Vercel, Netlify y GitHub Pages lo activan solos (con dominio propio también).
      2. Ningún secreto en el frontend ni en GitHub (estación 07).
      3. RLS activado en todas las tablas y reglas mínimas (estación 11).
      4. Validar en el servidor, no solo en el formulario (estación 10).
      5. Mostrar lo que escribe la gente como texto, nunca como HTML (estación 13): evita que alguien inyecte código.
      6. Verificación en dos pasos en GitHub, Vercel y Supabase. Quien entra en tu cuenta, entra en tu web.
      7. Copias de seguridad: el plan gratis de Supabase no las incluye. Exporta tus tablas (Table Editor → Export to CSV) de vez en cuando.

      La ley, en lo básico

      Esto es una orientación para entender qué piden las normas, no asesoramiento legal. Si una web es de una empresa real, hay que consultarlo con alguien especializado.

      • RGPD (Reglamento General de Protección de Datos, europeo) y LOPDGDD (la ley española): un nombre, un correo o una IP son datos personales. Si los recoges, tienes que decir para qué, durante cuánto tiempo, quién los guarda y cómo pedir que se borren. Eso es la política de privacidad, enlazada junto al formulario.
      • Recoge solo lo necesario (minimización): si para el libro de visitas basta con un nombre, no pidas el correo.
      • Dónde se guardan: al crear el proyecto de Supabase, elige una región de la Unión Europea. Simplifica mucho el cumplimiento.
      • LSSI-CE: si la web tiene actividad económica, necesita un aviso legal con los datos de quien está detrás.
      • Cookies: las técnicas (necesarias para que funcione la web) no necesitan permiso. Las de analítica o publicidad, sí: de ahí los avisos de cookies. Hay herramientas de estadísticas que funcionan sin cookies y evitan el aviso.
      • Accesibilidad: en España y en la UE es obligatoria para las administraciones y, cada vez más, para empresas que venden online. Lo que aprendiste en HTML que habla va por aquí.
